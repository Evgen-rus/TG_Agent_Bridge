# 05. Интеграция с AgentBridge и безопасность

## Факты из действующего репозитория на 16.10.2026

- Rick — suggest-only bridge: рабочие Telegram чаты → durable SQLite → эпизод → Codex → предложение владельцу. Автоматические клиентские ответы запрещены.
- SQLite Rick `runtime/agentbridge.sqlite3`; каждый отслеживаемый чат изолирован по своему контексту.
- Owner-диалог обрабатывается отдельно и не должен произвольно подменяться web-пользователем.
- Sally — отдельный бот/сервис и отдельный каталог данных: `runtime/sales_buddy/sales.sqlite3`, одна Telegram-тема — одна сделка.
- Sally имеет свои функции: рекомендации/текст клиенту, память по теме, договорённости и напоминания, ручное подтверждение спорных замен фактов, обработка изображений и аудио в существующем пайплайне.
- В документации описаны `rick.service` и `sales-buddy.service`. Перед деплоем сверить реальное состояние `systemctl`, окружение и настройки сети.

## Позиция по API

Нельзя просто «вебхуком имитировать Telegram-сообщения» и ожидать корректности: можно сломать auth/идемпотентность/topic provenance и разделение прав.

Codex должен выбрать минимальный входной adapter для существующих application/use-case методов:
- read-only запросы к авторизованным срезам SQLite через backend, не прямой доступ с frontend;
- серверная команда «задать вопрос» с валидированным actor/topic/scope, очередью и idempotency key;
- отдельные команды на approve/reject с сохранением audit trail и optimistic revision control;
- событие/stream статуса ответа (polling или SSE), но не фальшивое «готово».

## Разграничение

Роли: `owner` (Евгений), `rick_member` (Дмитрий), `sally_member` (Сергей). Реальные идентификаторы связываются через invitation/админское добавление, не жёстко закладываются в исходники.

| Операция | Евгений | Дмитрий | Сергей |
|---|---|---|---|
| Вход Rick | Да | Да | Нет |
| Вход Sally | Да | Нет | Да |
| Обычное общение в доступном продукте | Да | В рамках прав | В рамках доступных тем |
| Просмотр рабочих/клиентских данных | С учётом контекстного доступа | Только явно разрешённые Rick-чаты | Только разрешённые Sally-темы |
| Dev-действия / перезапуски / память | Только при подтверждённых правах | Нет по умолчанию | Нет |
| Подтверждение факта Sally | Только если допускает роль + workflow | Нет | Если допускает workflow |

Права реализуются на backend при **каждом** обращении, включая файл, поиск, stream и отмену. Проверка продукта недостаточна — должна проверяться и доступность конкретного chat_id/topic_id.

## Безопасность

- HTTPS с доверенным сертификатом, никаких временных публичных URL без защиты.
- Secure/HttpOnly cookies, CSRF mitigation, rate limit, login throttle, sessions revocation, audit logging sans PII.
- Не выводить `.env`, `auth.json`, raw клиентский диалог и документы в публичные ошибки/логи/репозиторий.
- Sensitive data нельзя автоматически кэшировать service worker, сохранять в localStorage или выводить в push без явного решения.
- Полный запрет public signup, API docs/internal diagnostics наружу.
- PWA offline shell может кэшировать только статические ассеты, без истории клиентов.
- SQLite WAL/lock стратегия: читать через штатные модули; для записи использовать существующие транзакционные инварианты, не править таблицы произвольно.
- Прежде чем модифицировать schema: backup consistent snapshot, migration tests, rollback plan, restore rehearsal.

## Production-путь

1. Инвентаризация инфраструктуры и способов доступа без раскрытия секретов.
2. Разработка/тестирование локально, отдельная ветка, review.
3. После выбора дизайна и готовых тестов: commit/push и только затем безопасный deploy.
4. На VPS: backup, `git status`, `git pull --ff-only` или эквивалент согласованной стратегии, сборка, минимальная конфигурация HTTPS, новые сервисы при необходимости.
5. Restart только затронутого сервиса; health smoke тесты. Не полагаться только на HTTP 200 — проверить реальную авторизацию и прежний Telegram функционал.
6. При проблеме rollback к ранее записанному commit и восстановление зависимостей/схемы по плану, без потери сообщений или DB.

**Блокирующие вопросы, если не может определить Codex:** адрес/домен, доступность SSH, законная модель раздельного доступа к рабочим и клиентским данным, способ безопасного создания пользователей, право использовать существующую подписку/модель из web-адаптера. Не выдавать «всё работает» без живых проверок.
