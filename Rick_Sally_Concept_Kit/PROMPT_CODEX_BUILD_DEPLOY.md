# ГОТОВЫЙ ПРОМПТ ДЛЯ CODEX — ФАЗА 2: РЕАЛИЗАЦИЯ + ДЕПЛОЙ

**Запускать только после того, как я выбрал и утвердил дизайн Rick и Sally.**

Мы работаем в репозитории `Evgen-rus/TG_Agent_Bridge`. Основной дизайн утверждён в предыдущем треде и выбранных prototyping changes. Входные материалы: `Rick_Sally_Concept_Kit.zip`, прототипы и мои утверждённые комментарии.

## Результат

Собрать **два независимых устанавливаемых PWA**, Rick для Евгения и Дмитрия, Sally для Евгения и Сергея. Общие UI-компоненты, но раздельные manifest/id/icon/scope/start_url, API policies, роли и данные. Никакого отдельного AI-агента: использовать штатные Codex/SQLite/workflow текущих Rick и Sally. Сохраняется работоспособность Telegram.

## Реализация

1. Проведи полный аудит backend, хранилища, Telegram-интеграции, прав и сервисов. Реальный код и тесты первичны.
2. Реализуй минимальный безопасный backend adapter для Web UI, не создавай параллельные конкурирующие Telegram polling-процессы. Совмести веб-операции со штатными transactional/inbox/workflow инвариантами. Для POST используй idempotency keys; при записи — честный статус подтверждения.
3. Реализуй серверный invite-only login для трёх пользователей и доступ к конкретным разрешённым чатам/темам. Дмитрий по умолчанию не получает owner/dev-доступ, Сергей — только Sally и разрешённые темы. Евгений может пользоваться обоими.
4. Добавь на выбранный UI реальные данные: Rick эпизоды/предложения/диалог с доступными контекстами; Sally темы-сделки, реальный контекст, ответы, договорённости, напоминания, утверждение фактов. Не рисуй фиктивные состояния; если API нет, явно сообщи и предложи безопасный минимальный контракт.
5. Сохрани существующие правила Rick suggest-only и Sally: подготовленный текст менеджер сам отправляет клиенту; изменение фактов только с проверенным подтверждением.
6. Голос/вложения/уведомления реализуй лишь при доказанной совместимости с существующим backend, иначе вынеси в следующий этап с честной пометкой.
7. Для PWA сделай корректные манифесты, оригинальные иконки, service worker только для статики (без офлайн-кэширования клиентской истории), HTTPS, Android-сборку/установку.
8. Реализуй корректную защиту сессий, CSRF, throttling, ACL в каждом endpoint, secure cookies, security headers, безопасное логирование. Не давай фронтенду прямой доступ к Codex auth/token/env/SQLite.

## Проверки до выкладки

Все текущие тесты проекта + новые API/Auth/e2e/regression tests. Проверки инъекции topic ID, запрета межпродуктного доступа, retries, дублей, конфликтов ревизий, ошибок Codex, восстановления после рестарта, long messages/media, Android 360/390/430px. Снимки/заглушки в тестах, реальные секреты не использовать.

## Автоматическая выкладка на VPS

Нужно **довести до работающего результата**, а не остановиться на PR, если необходимые доступы доступны в текущем окружении.

После успешных тестов:

1. `git status` и оценка изменений → commit → push по правилам ветвления проекта. Если требуется merge, выполните его штатным способом без force push.
2. SSH к действующему VPS, инвентаризация systemd/network/storage и review конфигурации без показа секретов в логах.
3. Снимки/consistent backup данных Rick и Sally с проверкой восстановления и записанной ревизией для rollback.
4. На VPS `git status`, убедись в отсутствии несохранённых изменений, fetch и безопасный pull нужного коммита (предпочтительно fast-forward), установка зависимостей, сборка frontend.
5. Используй существующую reverse proxy/HTTPS-инфраструктуру по возможности. Не перекраивай другой VPS проект. Новые домены/сертификаты выбирай только при наличии подходящих ресурсов; если для DNS нужна моя работа, задай один чёткий вопрос.
6. Перезапускай только затронутые сервисы (`rick.service`, `sales-buddy.service` — уточни реальную необходимость, а также новые web-процессы). Не делай бездумный restart всего VPS.
7. Проверь health, login/ACL, создание/отображение сообщений и реальную работу Rick и Sally в Telegram, без отправки сообщений в клиентские чаты. Подтверди наличие отдельного PWA manifest/scope каждого.
8. При критической ошибке — controlled rollback к зафиксированной версии без потери истории. Не объявляй работу завершённой, если smoke/acceptance failed.

## Автономность

Все безопасные технические операции — самостоятельно: файл, тест, commit, push, pull, install, configure, restart, check. Не запрашивай одобрение каждого шага; **не обходи** обязательные human-in-the-loop подтверждения внутри самих Rick и Sally. Нужны секреты/домен/доступ — спроси конкретно, не проси присылать секреты в чат.
